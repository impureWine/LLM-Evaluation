# 案例 C2：需求变更后的预算边界与“无解”表达

## 1. 案例信息

| 项目 | 内容 |
| --- | --- |
| 编号 | C2 |
| 类型 | 边界案例（补充边界测试），**不是模型失败案例** |
| 是否补测 | 是。属于补测设计，必须单列，不并入 18 次正式矩阵，也不进入成功率分母 |
| 依据 | 庄剀涵在[数据与场景说明](zhuang-kaihan-data-and-scenarios.md)第 139 行提出：把 change 第 2 轮预算设为 18.6 万元时应保留 B，设为 18.5 万元时应无合格车型 |

## 2. 边界在哪里

`fits()` 对预算用 `lte`，含等号，所以 18.6 万元的车刚好落在 18.6 万元预算内。第 2 轮预算一变，合格集合就从 2 辆收缩到 1 辆，再收缩到 0：

| 第 2 轮预算 | 第 2 轮合格集合 | 说明 |
| ---: | --- | --- |
| 19 万元（冻结版） | SIM-B | 与 `data/reference-answers-v1.json` 一致 |
| 18.6 万元 | SIM-B | 边界可行：刚好等于 B 的价格 |
| 18.5 万元 | 空 | 边界不可行：B 超出 0.1 万元，其余车型能源不符或超预算 |

也就是说：**19 与 18.6 是同一个解，18.5 是第一个“无解”点**。这条边界不是“模型答得好不好”，而是“需求本身还有没有解”。

## 3. 离线验证

验证复用 `dataset.py` 的 `constraint_history()` 与 `fits()`，只改内存中的预算数值，不动仓库数据：

```powershell
$env:PYTHONPATH = 'src'
python -m unittest tests.test_boundary_change -v
```

实际输出（2026-11-09）：

```text

test_no_solution_branch_cannot_reach_full_marks ... ok
test_honest_ledger_beats_silent_drift ... ok

```

三个用例分别锁定：边界从 1 辆变 0 辆、无解分支拿不到满分、诚实账本优于静默漂移。

## 4. 关键发现：无解分支与输出契约冲突

`prompts/output_schema_v1.json` 要求 `candidate_cars` 至少 1 项（`minItems: 1`）。所以在 18.5 万元这种无解分支里，模型**必须**给出至少一个候选，而任何一个候选都必然落在空集合之外：

- 第 2 轮约束符合度：候选越界，10 分必失；
- 第 4 轮约束符合度：最终推荐必然越界或为空，20 分必失；
- 第 3 轮多轮一致性：该轮要检查候选是否仍在有效集合内，候选越界即失分，5 分必失；
- 若某轮干脆返回空列表，则违反 Schema，整轮按 `turn_missing_or_invalid` 计 0，分数更低。

按冻结规则推算，**只要每条记录都必须通过结构校验，本分支的理论上限就是 65 分**（符合度 10 + 一致性 20 + 指令遵循 15 + 真实性 20）。构造样例已达到该上限：

| 假定表现（构造样例） | 符合度 | 一致性 | 指令遵循 | 真实性 | 总分 | 成功 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 保留 18.5 万账本，明说 B 超出 0.1 万，仍给出取舍 | 10 | 20 | 15 | 20 | **65** | 否 |
| 静默沿用 19 万结论，当作预算没变 | 10 | 0 | 15 | 20 | **45** | 否 |

两点结论：

1. 评分器**仍然能区分**“诚实报告接近选项”和“忘记新预算”，65 与 45 的差距主要来自一致性；
2. 但**上限被压到 65 分**，这不是模型能力不足，而是规则和 Schema 都没有为“无解”定义表达方式。若把这条边界放进正式矩阵，任何模型都会被打低分，属于**测量工具问题**，不能当作模型差异。

## 5. 处理建议

| 选项 | 做法 | 后果 |
| --- | --- | --- |
| A（推荐） | 18.5 / 18.4 这类无解变体**不进正式矩阵**，只作为补测观察“无解表达” | 正式矩阵保持 2 模型 × 3 场景 × 3 次，不破坏配额与统计口径 |
| B | 先改 Schema 允许空候选，并新增“无解”判定口径（空候选 + 明确说明 + 不编造 = 满分） | 可行，但要升协议版本、重算指纹、重跑全部批次 |
| C | 把边界换成“刚好可行”的 18.6 万，不用 18.5 万 | 仍能测边界保留能力，且不触发无解分支 |

建议 **A + C 组合**：正式矩阵不动；补测里用 18.6 万验证“新增预算刚生效时是否保留 B”，用 18.5 万只观察模型如何表达无解，不计分、不入库改分数。

## 6. 若执行补测：怎么做才不污染正式结果

1. **前置条件**：项目密钥、额度与团队授权（分工要求，当前均未满足）。
2. **执行人**：曾俊涛或李泉毅执行，关欣评分；不得由评分人自己跑模型以免口径走样。
3. **配置**：18.6 / 18.5 变体不在 `configs/evaluation-v1.json` 里，必须另存为版本化变体配置并记录指纹，不能临时改冻结文件。
4. **批次标注**：`evaluate.py` 在 `--repetitions 1` 时把批次标为 `pilot`；补测记录须在汇总时人工单列为“边界补测”，不得计入 18 次分母。
5. **次数**：每个变体 1 次即可，属探索性观察，不做统计推断。
6. **记录**：原始响应、变体配置、指纹、评分结果一并保存；结论只描述“这次怎么答”，不写“模型大概率会……”。

## 7. 局限

- 没有模型行为证据：本文所有分数来自构造样例，只证明评分器在无解分支的行为，不证明任何模型的表现。
- 构造样例的候选、账本、理由均为手写，可能比真实模型输出更“整洁”，因此不能拿 65 分当作“模型应得分”。
- 18.5 变体不在冻结数据内，若直接改 `configs/` 会破坏 `data/release-v1.json` 指纹与已有运行的可比性。
- 本案例不计入 18 次正式运行，也不改变成功率分母；如与正式结果同时呈现，须显式标注“补测”。
- 结论依赖当前权重与 Schema；若采纳建议 B（允许空候选），本案例的 65 分上限随之失效，须重新实测。
