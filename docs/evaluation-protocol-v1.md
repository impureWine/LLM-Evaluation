# 多轮购车评测协议 v1（结构化输出候选修订）

这是供双模型联调和冻结审核的候选版本。为支持可复核的参数对比表，当前候选修订将实验版本标记为 `v1.1-candidate`，并扩充共享 JSON 输出契约。团队仍需确认模型额度、完整试跑及评分口径，记录新的冻结提交后才能开始正式运行。已按旧提示词指纹生成的记录不得与新版本合并。

## 固定输入

[场景与车型清单](../configs/evaluation-v1.json)由本项目于 2026-11-07 编制，五款车及其配置均为教学模拟。年份为模拟款年，价格为不含税费、保险与优惠的模拟裸车价，单位为万元人民币。座位数单位为座，辅助驾驶级别按清单标签判断。基础任务使用固定清单并关闭联网。两个模型共享 [模型配置](../configs/models.json)中的生成参数和[提示词](../prompts/)。

每个任务四轮，依次为初选、补充或变更需求、逐车型参数对比、最终推荐。仅前两轮改变约束，后两轮沿用第二轮的约束。清单中的参考结果只供评分使用。候选数组和最终推荐以 JSON 保存；第三轮同时输出 `parameter_comparison` 数组，每个候选逐项列出来源编号、车型、配置、年份、价格、能源、座位和辅助驾驶。运行器检查其行与有效候选完全对应，参数与固定输入完全一致，并将差异写入审计字段。其他轮次此数组为空。`why_fit` 仍保存模型的自然语言解释，不能代替结构化参数表。

## 半自动评分

### 1. 口径与执行方式

评分对象是 `runs/<批次>/<run_id>.json` 四轮记录，满分 100。规则文本以本节为准，`src/llm_eval/scoring.py` 是可执行实现，二者必须在同一提交中冻结；不一致时以本节为准并修正代码。代码只读运行记录，不调用模型接口。

规则分两类：程序可判定的项目自动计分；无法机械判定（例如纯文本参数陈述、无参数合并表的历史批次）的项目进入 `review-queue.csv` 待人工判定，人工回填 `verdict` 后重跑同一命令重算，不手工改分。

```powershell
$env:PYTHONPATH = 'src'
python -m llm_eval.scoring --runs runs/<批次>
# 人工复核后
python -m llm_eval.scoring --runs runs/<批次> --review runs/<批次>/scores/review-queue.csv
```

输出：`scores.csv`（逐次分数与失败项）、`summary.csv`（模型×场景汇总）、`review-queue.csv`（待判定项）、`review-hints.csv`（仅提示，不影响分数）、`report-scores.csv`（可直接传给 `python -m llm_eval.report --scores`）、`summary.md`、`scores.json`。

`review-queue.csv` 的 `kind` 列区分两类：`blocking` 表示缺证据、分值暂记 0，人工判定前不计入成功；`override` 表示自动已判不通过但允许人工改判，`default` 列记录自动结论。两类都必须填 `verdict`（`pass`/`fail`）才算复核完成，改判理由另记在案例或复核记录中。

### 2. 分值分配

权重依据：多轮购车任务的工程价值首先在于“给出的车能不能买”（约束符合度 40），其次是“多轮里有没有丢约束或改口径”（25），再次是“是否按要求给出结构化产物”（15），事实错误直接毁掉结论所以单列真实性 20。

| 指标 | 分值 | 轮次拆分 |
| --- | ---: | --- |
| 约束符合度 | 40 | 第 1 轮 10、第 2 轮 10、第 4 轮 20 |
| 多轮一致性 | 25 | 第 2 轮 10、第 3 轮 5、第 4 轮 10 |
| 指令遵循 | 15 | 第 1 轮 3、第 2 轮 3、第 3 轮 5、第 4 轮 4 |
| 信息真实性 | 20 | 每轮 5 |

每一项按“通过得分、不通过得零”的二值方式记分，不设半分。未通过项必须留下原因代码，代码与中文说明的对应见代码中的 `reason` 字段。

### 3. 车型身份匹配与事实核验

车型以配置、年份和来源编号三者共同识别。

- 通过：`evidence_ids` 命中固定车型库，且候选的 `model`、`trim`、`year` 与库中该来源编号一致。
- 只靠车型名匹配、缺来源编号，或来源编号指向另一车型、库中不存在，都不算通过。前者记为 `identity_fields`，后者记为编造。身份不通过只扣信息真实性，不重复扣约束符合度。
- 事实核验：`year` 精确相等；`price_wan` 容差 ±0.01 万元（仅容纳四舍五入）；`energy`、`seats`、`adas` 精确相等。第三轮以 `parameter_comparison` 合并出的行核验，无该字段的历史批次转人工。

### 4. 约束账本判定

从每轮 `effective_constraints` 提取可核对字段：预算（万元数值，视为上限）、座位（整数，视为下限）、能源（单一取值）、辅助驾驶（取文本中的最高等级标注）。无法归入这四类的自由文本不参与计分，也不去掉分。

- 保留：仍生效的硬约束必须以 `active` 出现且不被放宽——预算不高于用户要求、座位不低于要求、能源与辅助驾驶等于要求。能源写成“纯电或插电混动”等并列取值，按放宽处理。
- 生效：`source_turn` 等于当轮的新增或替换约束必须为 `active`。
- 替换：被替换的旧预算不得再以 `active` 出现；显式标为 `superseded` 才视为完整记录，静默消失只记 `review-hints.csv` 提示，不退分。
- 第三轮：该轮没有约束符合度项，因此在此检查候选是否仍落在当轮有效集合内，用来发现“新约束没生效却继续沿用旧候选”。

同一处错误可能同时落在符合度与一致性上，这是权重设计的结果，不额外做互斥处理。

### 5. 指令遵循

每轮前置条件：结构校验通过，且第 1—3 轮的 `next_question` 不超过一个问句（按问号计数）。第 4 轮要求给出单款车型、非空理由和非空取舍列表。

- 第 1 轮：候选列表非空。
- 第 2 轮：更新后的候选列表非空。
- 第 3 轮：用 `parameter_comparison` 检查是否覆盖全部已匹配候选，并要求运行器的 `comparison_audit` 通过；仅旧指纹批次没有该字段时，才退化为检查 `why_fit` 是否同时出现价格数值、能源、座位数和辅助驾驶等级。
- 第 1、2、4 轮：`parameter_comparison` 必须为空数组；非空按该轮指令遵循不通过计，依据是运行器 `comparison_audit` 的对应审计项。

按问号计数是可复现的近似口径，不追求语义精确。出现“一个问号里含两件事”或“两个问号但只有一个二选一”的边界情况时，该项以 `override` 进入复核队列：自动结论仍为不通过，人工可凭完整上下文改判为通过，但必须记录改判理由。若同轮还失败其他不可改判的检查（如候选列表缺失），整项不得改判，避免一次改判连带放过其他缺陷。

### 6. 信息真实性

每轮 5 分：该轮全部候选通过第 3 节的身份匹配与事实核验才得分，任一提及编造车型、错误参数或错误来源编号，该轮为零。第 4 轮另检查最终推荐能在固定库中定位。第 3 轮另核验模型输出的 `parameter_comparison` 数组：运行器 `comparison_audit` 必须通过（每行与有效候选一一对应，且价格、能源、座位、辅助驾驶与固定库一致），不通过则本轮为零；旧指纹批次没有该字段时，退化为逐行回查固定库并转人工复核。

缺少可核验渠道时不自动判通过：该项记 0 分并进入 `review-queue.csv`，人工确认后才计入。

### 7. 缺失、异常与纠正重试

轮次缺失、结构校验失败、超时或中断，该轮所有检查项按不通过计，原因记为 `turn_missing_or_invalid`，不按“未发起”剔除。纠正重试成功不重复扣分，但 `correction_attempts` 与全部尝试计入成本统计。补跑单独成批，不改写原批次文件。

### 8. 成功定义与汇总口径

任务成功＝四轮均通过结构校验、最终推荐落在当轮参考集合内、信息真实性得满分。成功率分母为计划内已发起的任务，失败、超时及中断计入分母；未发起项单列。含待复核项的运行在确认前不计入成功数，汇总中单独列出。

同一场景三次运行报告均分、最小值、最大值与标准差，并给出成功数；多款合格车型之间的切换按同一口径评分，不视为不稳定。汇总另记推荐分布（各车型被最终推荐的次数），只作描述性统计，不参与打分，也不据此判断稳定性。耗时取任务墙钟时间，token 按各轮可读到的用量求和，缺失单列、不填 0。图表与表格须注明指标含义、单位、样本数及是否包含失败任务。

### 9. 本版明确的判定口径

以下决定由评分负责人在冻结前确认，改动须按第 10 节升版本。

| 编号 | 问题 | 本版决定 |
| --- | --- | --- |
| D1 | 候选是否必须列全合格集合 | 不要求列全，非空且不越界即可；漏掉唯一合格车型会在第 2、4 轮自然失分 |
| D2 | “最多一个追问”如何计 | 按问号计数自动判，1—3 轮超过一个问句即失掉该轮指令遵循分；该项可人工改判，连同理由留痕 |
| D3 | 第三轮参数表如何判定 | v1.1-candidate 起第三轮必须输出 `parameter_comparison`，按表与运行器审计判定；仅旧指纹批次无表时退化为 `why_fit` 文本检查并把真实性项转人工 |
| D4 | 事实核验容差 | 价格 ±0.01 万元，年份、能源、座位、辅助驾驶精确相等 |
| D5 | 纠正重试后通过 | 不重复扣分，但纠正次数与全部尝试计入成本 |
| D6 | 同一错误是否两处扣分 | 按维度各自判定，不做互斥；符合度看结果，一致性看账本 |
| D7 | 多款合格车型切换 | 不扣分；汇总额外记录推荐分布作描述性统计 |
| D8 | 权重是否调整 | 维持 40/25/15/20，依据见第 2 节 |

## 运行顺序

在仓库根目录执行：

```powershell
$env:PYTHONPATH = 'src'
python -m llm_eval.evaluate --dry-run
# 确认本地密钥、额度和团队授权后执行联调，每个模型和场景一次
python -m llm_eval.evaluate --allow-disabled-model --repetitions 1
# 完成联调及冻结审核后，从冻结提交开始运行三次重复
python -m llm_eval.evaluate --allow-disabled-model
```

联调批次标为 pilot。完整矩阵的日志标为 evaluation_candidate，只有冻结提交与实跑条件核对无误后才可纳入正式统计。日志保存在 Git 忽略的 runs 目录；公开前先脱敏。三次重复计划为两模型 × 三场景 × 三次，合计 18 次，每次四轮。

团队完成冻结并生成完整矩阵后，再运行 `python -m llm_eval.report` 导出候选、参数对比、最终推荐、逐次摘要、按模型和场景汇总及 SVG 图表。它只读取与当前车型、提示词及评分指纹一致的 `evaluation_candidate` 日志，不读取 pilot。结构化完成率不等于约束得分或100分总分；事实核验范围见[结果提取说明](results-report.md)。
