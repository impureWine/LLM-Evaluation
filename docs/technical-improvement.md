# 技术改进方案：结构化输出校验与受控修复

## 1. 实测问题

购车决策任务的自动评分依赖候选车型、有效约束、最终推荐和来源编号。若模型输出自由文本或
不稳定的 Markdown JSON，解析程序可能在以下位置失败：

- 在 JSON 前后添加解释或代码围栏；
- 缺少 `evidence_ids`，导致推荐无法回溯车型库；
- 同时给出最终推荐和追问，状态自相矛盾；
- 将已撤销预算继续当作有效约束；
- 推理 token 已耗尽输出上限，最终答案为空白；
- 字段拼写或类型变化，使后续汇总脚本直接中断。

这些问题不是单纯“模型答错”，而是模型输出和工程数据契约之间的断层。

## 2. 选取的改进方案

方案 B 为当前实现：**JSON 模式 + Schema 校验 + 最多一次受控纠正**。

处理链如下：

1. 两个模型使用相同的 `response_format={"type":"json_object"}`。
2. 提示词嵌入版本化 JSON Schema。
3. 收到输出后先解析 JSON，再检查顶层字段、候选车字段、来源编号、状态枚举和
   `finish_reason`。
4. 校验通过则立即保存结构化结果。
5. 校验失败时，将具体错误和原响应加入同一对话，追加一条统一纠正消息，再请求一次。
6. 纠正仍失败则保留为 `valid=false`，记录失败原因，不静默丢弃或人工补写模型答案。

纠正不是无限重试。每个模型最多一次，且纠正消耗的 token、延迟和次数全部计入该次任务成本。
这避免高能力模型通过更多格式重试获得不公平优势。

## 3. 备选方案比较

| 方案 | 做法 | 优点 | 缺点 | 适配当前项目 |
| --- | --- | --- | --- | --- |
| A：仅提示词约束 JSON | 在提示词中要求输出 JSON，不做平台 JSON 模式，也不校验 | 实现最少；跨平台门槛低 | 格式失败直接进入解析器；无法及时定位坏样本 | 作为消融基线 |
| B：JSON 模式 + 校验 + 一次纠正 | 当前实现 | 对当前两个模型可用；能保留失败证据；工程复杂度适中 | 增加格式检查代码；纠正会增加 token 和延迟 | 采用 |
| C：工具调用或原生结构化输出 | 定义 JSON Schema 工具并强制调用，或使用平台原生严格 Schema | 框架约束通常更强；适合复杂工具链 | 不同平台对 Schema 子集和能力支持不一致；会同时改变输出协议，难以与纯对话任务公平比较 | 留作后续扩展 |

没有选择方案 C 的直接原因不是它一定更差，而是当前两个模型位于同一兼容接口，团队首要目标是
得到可解释、可复现的购车决策结果。方案 B 用较小改动获得可操作的结构保障，也不会把
“是否会调用工具”混入本轮主要比较。

## 4. 为什么它不是只改提示词

提示词只表达期望，校验器负责验证合同：

- JSON 解析失败会被记录为具体行列；
- 缺失字段会给出 JSON 路径；
- `evidence_ids` 为空会被判失败；
- `finish_reason=length` 即使碰巧得到部分 JSON，也不会被当成成功；
- 纠正是统一模板，两个模型条件相同；
- 失败样本仍可进入关欣的边界案例分析。

因此该方案把“模型应该输出什么”和“程序如何证明输出可用”分开，便于测试与维护。

## 5. 验证方法

### 5.1 实验设计

正式 18 次运行仍用于团队主评测。技术改进另设为标注清楚的补充消融实验，不重复使用主实验记录：

- 条件 A：仅提示词要求 JSON，关闭 JSON 模式和纠正；
- 条件 B：当前 JSON 模式、Schema 校验和最多一次纠正；
- 两个模型 × 三个正式场景 × 每场景三次重复 × 两个条件，共 36 次补充运行；
- 每组使用同一车型库、用户脚本、场景、参数和提示词主版本；
- 随机化运行顺序，避免平台短时波动总落在同一条件；
- 每个任务标记 `experiment_type=technical_ablation`。

### 5.2 指标

| 指标 | 定义 | 主要用途 |
| --- | --- | --- |
| JSON 解析率 | 成功解析 JSON 的次数 / 有效首次请求数 | 判断格式是否可进入下游 |
| Schema 通过率 | `valid=true` 的最终次数 / 任务数 | 衡量完整数据契约 |
| 首次通过率 | 无纠正即 `valid=true` / 任务数 | 区分模型原生格式能力与修复收益 |
| 纠正成功率 | 纠正后通过 / 首次失败任务数 | 判断修复机制是否值得 |
| token 开销率 | `(token_B - token_A) / token_A` | 计算格式工程的资源代价 |
| 延迟开销率 | `(latency_B - latency_A) / latency_A` | 计算用户等待代价 |
| 约束符合度 | 仍按关欣评分规则计算 | 防止格式通过但业务正确性下降 |

样本较少时应报告中位数、范围或自助法置信区间，不能只报告均值。成功率建议同时给出分子和分母。

### 5.3 预先设定的判断标准

建议在正式运行前由团队冻结以下验收门槛：

1. 条件 B 的 Schema 通过率不低于 95%。
2. 条件 B 比条件 A 提高至少 15 个百分点，或条件 A 已达到 95% 且 B 不低于 A。
3. 平均 token 开销不超过 15%，且中位延迟开销不超过 20%。
4. 约束符合度下降不超过 3 个百分点。
5. 纠正成功率低于 20% 时，应重新评估是否保留纠正步骤，避免为极少数样本普遍增加成本。

这些数值是当前建议，团队成员可在正式运行前统一调整并记录版本。不能在看到结果后临时改变门槛。

## 6. 当前验证状态

2026-11-07 的冒烟测试已经验证：

- 两个模型均接受统一 JSON 模式；
- 两个模型首次输出均通过当前 Schema；
- 两个模型的 `finish_reason` 都是 `stop`；
- 纠正调用在本次样本中均为 0；
- Schema 失败和纠正路径已通过离线单元测试。

这只证明实现链路可用，不证明改进已经带来统计显著的准确率提升。正式 A/B 结果仍需按上述方案
补充运行后由张王昊、程杰和关欣共同核验。

## 7. 风险与回退

- 若后续模型不支持 `json_object`，不得直接删除该参数后仍宣称条件相同；应建立独立配置并从
  公平性说明中披露。
- 若纠正经常造成重复长回答，可把最大纠正次数降为 0，仅保留校验和失败记录。
- 若平台原生严格 Schema 稳定支持两个模型，可在下一版本比较方案 C；但必须重新跑基线。
- 所有失败原文、错误和重试都要保留，避免只统计成功样本造成幸存者偏差。
