# 软件工程层次分析（李泉毅）

本节分析本次购车决策评测程序和所接入的模型服务。模型服务内部架构、训练数据及推理实现不在本项目可观测范围内，因此不依据输出推断模型内部机制。

## 程序层面

评测将一次购车任务表示为四轮有序对话；`ChatMessage` 列表维护同一任务的上下文，车型库、模型注册表和场景清单以版本化 JSON 表示，批次由模型、场景和重复次数组合生成。`evaluate.py` 按轮调用结构化客户端，Schema 校验失败时执行受限纠正，并记录每轮原始响应、解析载荷、服务模型标识、请求延迟、token 用量及纠正次数。

第三轮车型参数表从模型候选的来源编号关联回冻结车型库，参数值直接取数据集，不从自然语言解释中猜测；无法与来源编号及车型、配置、年份同时匹配的候选单独标为未匹配，不填造参数。该处理让表格事实可复核，但不能单独证明模型已在文本中正确解释这些参数，仍需用输出契约和评分规则评价。

## 软件工程层面

项目把配置、提示词、模型适配、Schema 校验、任务编排和实验协议分开维护。配置记录模型标识、平台、参数、超时与重试设置；提示词包生成指纹；联调运行和正式候选批次分开标记；每次批次写入独立目录，单次运行文件采用独占创建，避免补跑覆盖原始结果。离线测试覆盖配置、提示词、接口重试、Schema 和运行流程，便于在无 API 额度时验证基础行为。

主要风险仍在跨层边界：结构合法不代表推荐符合预算或现实需求，必须由独立规则与人工核验；车型数据错误会让模型比较“正确地”得出错误结论；服务端已完成推理但响应超时可能导致重试和重复计费；日志含原始回答，公开前需脱敏。建议继续补充来源编号到每个字段的审计、预算/能源/座位等硬约束的回归测试、异常注入测试，并在报告中区分计划任务、已发起任务、接口完成任务和评分成功任务。

## 商业层面（待补官方来源）

本项目消费的是模型平台的 API 服务。一般可从推理额度或 token 用量、模型能力与延迟、服务稳定性、开发者工具及生态支持比较供应商；但具体价格、免费额度和模型定位会变化，必须由团队补充测试日期对应的官方 API 文档、模型目录与价格页链接后再写成事实。本仓库的实验配置和日志没有提供可核验的费用数据，因此本文不列具体单价，也不据此判断哪家平台整体商业竞争力更强。

## 可得结论

模型服务选型是软件工程决策的一部分，但不能只看单次回答。应结合统一实验条件下的任务得分、失败案例、延迟、token 消耗和数据/接口风险；结论仅适用于本次冻结的数据、场景、模型标识与参数，不构成行业整体排名。
