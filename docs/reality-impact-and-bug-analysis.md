## 一、大模型对现实生活的影响

### 1. 它改变的是决策过程，而不是替人做决定

购车是低频、高金额、参数密集的决策：预算、能源、座位、辅助驾驶几项硬约束互相牵制，还要在几十款车里比参数、查口碑、算落地价。这类任务里，大模型的第一层价值不是“给出结论”，而是把“翻资料、列候选、做对比表”这段体力活压缩成一次对话。

本次评测的任务设计正是围绕这一点：四轮里，程序要求模型先给候选、再按新增约束更新、再逐车型列参数、最后给一款推荐并说明取舍。模型的输出不是一段散文，而是带来源编号的结构化结果——这意味着它可以被程序直接消费、被离线核对、被批量比较。**对现实生活的影响，首先体现在“决策过程是否可复核”，而不是“答案是否聪明”。**

### 2. 结构化输出，让“会聊天”变成“能被集成”

本次输出契约要求 JSON、要求候选带 `evidence_ids`、要求最终推荐包含理由与取舍。这一层约束看似只是格式，实际决定了大模型能不能嵌进真实业务：只有字段稳定，才谈得上自动入库、自动对比、自动告警。

反过来看，格式合法并不等于内容合规。案例 C1 里，模型输出的 JSON 结构校验完全通过、`finish_reason` 为 `stop`、零重试，但追问字段里塞了两个并列问题。**结构校验能证明“字段都在”，证明不了“事情做对了”。** 这类“看起来规范”的错误，比明显的乱答更难被普通用户发现。

### 3. 核验成本从“找不到信息”转移到“分不清真假”

过去买车做功课的难点是信息分散：参数在官网、口碑在论坛、价格在 4S 店。模型把信息集中之后，难点变成了判断哪一句可以信。

购车场景的代价很具体：编造一个不存在的配置、把 17.6 万说成 16.7 万，用户可能要跑到店里才发现。本次固定车型库只有五个字段（年份、价格、能源、座位、辅助驾驶），没有续航、油耗、保值率；模型对这些未提供字段的处理，正是幻觉最容易发生的地方。因此评分规则把“信息真实性”单列 20 分，并要求候选必须能用来源编号在固定库中定位，而不是靠车名相似就算通过。

对普通用户来说，这意味着一个新的使用习惯：**看结论之前先看来源和日期**。对产品来说，这意味着“来源卡片”不是装饰，而是功能的一部分。

### 4. 遗忘约束比答错更隐蔽

多轮场景里最危险的错误不是“不知道”，而是“忘了”。案例 C2 的离线验证显示：需求变更那一条，预算从 24 万元改成 19 万元后，合格车型从 2 辆收缩到 1 辆；再降到 18.6 万元仍是 1 辆，降到 18.5 万元则一辆都不剩。

如果模型在第二轮之后还沿用旧预算，用户拿到的就是一辆超预算的车。更麻烦的是，这种输出往往“看起来很有条理”：候选、参数、理由一应俱全，只是前提已经过期。本组评分因此把“多轮一致性”设为 25 分，专门检查约束账本有没有保留、新增有没有生效、被替换的旧预算有没有标为 `superseded`。

这也解释了为什么“多款合格车型之间换一个推荐”不算不稳定，而“预算消失了”必须扣分：前者是合理偏好，后者是决策前提被悄悄改写。

### 5. 等待时间决定了它能被用成什么形态

现有记录里，单轮完整请求的延迟差异很大：当前主模型 `glm-4.7-flash` 在关闭思考模式后单轮仍需 89.282 秒；更早的接入冒烟（DeepSeek 两个模型，仅作跨平台历史参考）分别为 12.5 秒与 31.9 秒。

一次购车任务要四轮。按 89 秒估算，用户实际等待可能达到数分钟。这直接决定了产品形态：它适合“提交需求、等结果、再回来核对”的异步助手，不适合“边聊边等”的实时对话；也决定了失败重试的成本——一次超时可能意味着几分钟白等。延迟不是体验细节，而是会不会被用起来的分水岭。

### 6. 对从业者：评测能力正在变成工程能力

同一份提示词、同一套车型数据，不同平台的输出质量、延迟和成本差异明显。没有可复现的评测，选型只能靠感觉；有了评测，才谈得上“这个场景用便宜模型、那个场景用推理模型”。

本次实践里，真正花时间的不是写调用代码，而是：固定数据与场景、把预期结果写成可计算的参考集合、把评分规则写成代码并给它写测试、把失败和补测分开记录。这些工作和大模型本身无关，属于软件工程的常规能力——这可能是这门课最想让同学们体会的一点。

### 7. 风险与责任边界

- **幻觉在参数上代价最高**：车型、配置、价格都是硬事实，错一个数字就可能误导消费决策。本次用固定题库 + 来源编号 + 真实性评分来压缩这个空间，但不能消除。
- **数据时效**：车型价格会变，模型训练数据不会跟着变。任何购车助手都必须把“数据日期”和“价格口径”带在输出里，否则结论不可用。
- **责任归属**：模型给建议，用户承担后果。产品层面需要明确“这是信息整理，不是购车建议”，并在无解、超预算等边界上给出可理解的解释。
- **评测本身的偏差**：只看成功案例会高估模型，只看失败案例会低估。本次坚持保留冒烟失败、pilot 与补测记录，就是为了避免“幸存者偏差”。
- **信息不对称可能缩小也可能放大**（推断，未验证）：模型能帮不会查资料的人快速建立框架，但也可能因为训练数据偏好而集中推荐少数热门车型。本次实验没有足够样本支持任一方向的结论。

### 8. 小结

本次评测能支持的判断是有限的：单场景、教学模拟数据、每场景三次运行，还不足以推断真实购车行为会怎样改变。但有一件事比较确定：**大模型进入生活的方式，不是替人拍板，而是把“整理信息、比较选项、解释取舍”这件事变得更快、更便宜；它能不能被信任，取决于约束能不能被记住、事实能不能被核对、错误能不能被发现。** 这三条，正好对应本次评分的三个维度，也是产品能不能落地的三条底线。

## 二、软件工程建议与 BUG 原因分析

### 1. 先分层：问题出在哪一层

把观察到的问题按“模型 / 数据 / 提示词 / 解析与评测程序 / 接口服务”分开，是避免“一有错就怪模型”的前提。下表只列有记录支撑的现象，未观察到的内部机制一律标为假设。

| 编号 | 现象 | 直接来源 | 证据 | 性质 |
| --- | --- | --- | --- | --- |
| P1 | 追问字段含两个并列问题，但结构校验通过 | 模型输出 + 提示词约束缺失 | 案例 C1、冒烟记录 `parsed_output.next_question` | 观察 |
| P2 | 无解分支下理论上限只有 65 分 | 规则与输出契约 | 案例 C2、`tests/test_boundary_change.py` | 观察（离线实测） |
| P3 | 关闭思考模式前，完整请求 3 次尝试后仍失败 | 接口服务 / 参数 | `evidence/zhipu-glm-4.7-flash-smoke-2026-11-07.json`，`TransportError` | 观察 |
| P4 | 单轮延迟 89.282 秒 | 服务端推理 + 参数 | 成功冒烟记录 | 观察 |
| P5 | 第 3 轮参数表在旧格式下无法自动核验 | 解析与评测程序 | 协议第 5 节、`parameter_comparison` 尚未合并 | 观察 |
| P6 | 对照模型 `glm-4.7` 始终未实跑 | 流程 / 授权 | `configs/models.json` 中 `enabled: false` | 观察 |
| P7 | 正式 18 次批次尚未汇入 | 执行进度 | `runs/` 为空 | 观察 |

### 2. 逐层归因

**2.1 模型层（待程群核验补充）**

可疑表现在 P1：模型把“二选一”和“补充要求”合并在一次追问里。这属于生成策略，内部不可观察，只能列为假设：一种可能是模型倾向一次收敛多个不确定性以减少轮次；另一种可能是它把“一个复合问句”理解成了“一个问题”。**在拿到更多样本前，不应断言这是模型缺陷**——也可能是提示词没有给出正例。

**2.2 数据层**

固定题库只有五款教学模拟车，可核验的约束字段只有价格、座位、能源、辅助驾驶四项（年份用于身份识别），且价格明确标注为模拟裸车价。好处是可控、可复现；代价是覆盖面窄：续航、油耗、保值率这些真实购车最关心的字段没有，模型一旦自行补充就无法核对。这不是数据错误，而是**数据契约的边界必须在评测结论里写清楚**。

**2.3 提示词层**

`prompts/system_v1.md` 明确要求“最多提出一个最关键的问题”“`next_question` 必须是单个具体问题”，但 `output_schema_v1.json` 对 `next_question` 只约束为字符串或空，没有任何语义检查。**要求写在自然语言里，校验写在结构里，两者之间有空隙**——P1 就是从这个空隙漏过去的。

**2.4 解析与评测程序层**

P5 是最典型的工程问题：第 3 轮要求逐车型列参数，一期实现只在 `why_fit` 文本里保留，程序无法可靠提取。补救方案（`parameter_comparison`）虽已实现，但尚未合并；在此之前，该项只能进人工复核队列。这说明**评测程序的解析能力会反过来限制评分口径**：解析不了的东西，最后都会变成人工成本或主观打分。

另一个自我提醒：评分器本身也是被测对象。本次给评分子写了 18 个用例、给边界写了 3 个用例，就是为了防止“评分器的 bug 被当成模型差异”。

**2.5 接口服务层**

P3 的记录很明确：`TransportError`，`Request failed after 3 attempt(s)`，失败记录里没有保存每次尝试的明细。关闭思考模式后成功。可以确认的是“该请求在当时的参数下无法完成”；**不能确认的是“超时由思考模式导致”**——这是一次改动前后对比，不是控制变量的 A/B 实验，因果应标为假设。P4 的 89.282 秒也说明，即使关掉思考，服务端延迟仍是使用体验的主要变量。

### 4. 不建议做的事

- **不要为了让案例好看而重跑覆盖原记录**：失败样本本身是证据，补跑另起批次。
- **不要用补测结果改写正式分数**：18.5 万元那条边界不进 18 次矩阵，也不进成功率分母。
- **不要在冻结后改提示词或评分规则**：改了就要升版本、重算指纹、重跑，新旧批次不能混算。
- **不要用“人工看一眼觉得对”代替评分规则**：人工复核可以改判，但必须留理由、进队列、可追溯。

### 6. 局限与待回填

- 本节所有判断基于冒烟记录、离线数据校验与两个边界案例，**没有一个判断依赖正式 18 次结果**；正式结果到位后需要复核“成功率、波动、延迟、token”相关的表述。
- P1 只有一次调用样本，不能推断发生率；P3 只有一次失败记录，不能推断超时概率。
- 模型内部机制（为什么同时问两件事、为什么超时）无法直接观察，相关段落已标为假设。
- 权重与口径按协议 v1.0 冻结；若采纳“允许空候选”的方案，C2 的 65 分上限失效，本节结论需同步修订。
