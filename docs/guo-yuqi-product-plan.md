# 郭昱祺：购车决策助手的产品规划与NABCD分析

负责人：郭昱祺（102400413）。日期：2026-11-09。状态：基于现有证据的设计方案，采访与正式实验后修订；**不是已上线功能或已验证的商业收益**。

## 1. 产品目标与证据来源

在当前GLM模型接入之上，设计能说明“条件如何变化、哪些车合格、参数从哪里来”的购车决策助手。首版沿用五款教学模拟车验证流程，目标用户假设为首次选车者、家庭换车者，以及整理咨询需求的开发者/客服。学生采访只验证其操作体验，不自动代表这些真实购车群体。

| 输入编号 | 已知事实或缺口 | 对规划的影响 |
| --- | --- | --- |
| R01 | [Flash冒烟](../evidence/zhipu-glm-4.7-flash-smoke-success-2026-11-07.json)有正确候选及来源编号，但一个追问字段内有两个问题，仍通过Schema | 同时核验结构与语义；一次澄清只处理一个必要事项 |
| R02 | [场景脚本](../configs/scenario-rules-v1.json)要求第2轮新增条件或替换预算，[参考集合](../data/reference-answers-v1.json)可独立计算 | 展示有效条件和变更历史，按当前条件重新筛选 |
| R03 | [数据说明](zhuang-kaihan-data-and-scenarios.md)明确模拟裸车价，且未提供续航、油耗和保值率 | 显示口径、配置和日期；未知留空，不能用模型记忆补齐 |
| R04 | 冒烟记录为一次89.282秒非流式调用；[当前配置](../configs/models.json)关闭流式和思考，GLM-4.7禁用 | 等待反馈值得验证；现有证据不足以选择更快/更优模型 |
| R05 | [市场与商业资料](zhuang-kaihan-market-and-business.md)区分品类用户、实际购车者和付费客户 | 不用宏观用户规模代替本产品需求或营收验证 |
| R06 | 尚无真实学生采访和正式18次对比结果 | 先形成可执行假设；保留用户反馈修改优先级的入口 |

## 2. NABCD

| 要素 | 分析与设计选择 |
| --- | --- |
| **N：Need，需求** | 用户要在预算、座位、能源等条件下形成可核验的候选，并在需求改变时及时排除旧候选。假设H1：条件及来源可见能减少回看和反复确认；H2：明确未知项能提升判断质量。需求来源为R01–R03与任务分析，尚未通过真实用户验证。高代价的错误包括把裸车预算误当落地预算、遗漏7座要求、沿用旧预算或引用错误配置。 |
| **A：Approach，做法** | 自然语言输入→条件确认→程序硬筛选→模型解释→输出校验→来源可查的比较/推荐。条件带来源轮次与active/superseded状态；来源卡片记录年份、配置、价格口径、数据日期。模型负责组织解释，程序负责对固定字段判定与回查；每轮重新计算可行集合。没有合格项时说明冲突，任何放宽都需用户明确选择。 |
| **B：Benefit，收益/成本** | 预期减少重复整理条件、复制参数和人工回查的时间；发生变更后用户能直接看到候选增减及原因。代价是数据维护、语义检查和界面信息密度。以硬约束通过数、核验任务用时、求助次数和完整任务延迟验证收益；费用计算包含失败、纠正、历史上下文和数据维护，不能只看免费token。 |
| **C：Competition，竞争与替代** | 通用聊天工具覆盖广且输入门槛低，汽车垂直平台有车型/报价与交易生态，手动表格透明但维护繁琐。本方案先把“多轮条件变更、可重算候选、事实来源回查”整合到一个过程。差异化是这个可审计流程，尚未证明竞争者没有同类功能；不以缺少实测的模型排名作卖点。 |
| **D：Delivery，触达与交付** | 先在课程内提供固定数据的可复现实验及学生试用，收集匿名操作问题；再邀请有实际选车需求的人验证；来源维护可行后再与汽车内容平台或咨询团队试点。用户可下载条件、比较和来源报告，不必依赖聊天记录回溯。收费可试验单次报告或企业辅助订阅；渠道、价格及转化率目前均为假设。 |

用户可能采用它的原因是“改一个条件就能看到候选变化，并验证解释”，采用前提是车型数据可靠且任务完成成本可接受。若采访表明用户更需要真实报价或落地价核算，应记录反证并调整路线，不能用P0规划反推用户需求。

## 3. 关键交互与创新点

首屏收集用途、预算口径和硬约束，用户先确认系统理解的条件。后续将“预算24万元→19万元，第2轮生效”显示为清晰变更，保留能源和座位要求。以周末跨城场景为例，SIM-C从第2轮起因22.6万元超过19万元而退出，SIM-B继续符合；这只是固定输入的预期行为，不是模型实测结果。

候选比较按同一组字段展示，未知续航显示“未提供”，每条事实能打开来源卡片。最终报告包含推荐、满足条件的理由、被排除项、取舍和待核验事项。若只剩一辆，说明为什么只有一辆；不为凑齐2–5款而编造或放入不合格车。L2沿用数据标签，不能改写成可无人驾驶。

```mermaid
flowchart LR
  A[用户描述或修改需求] --> B[确认当前有效条件]
  B --> C[车型库硬约束筛选]
  C --> D[模型组织比较和解释]
  D --> E[结构与语义及来源核验]
  E --> F[比较表和来源卡片]
  F --> G[带版本的推荐报告]
  F --> A
```

创新点在于把条件版本、确定性筛选和事实证据结合起来；模型厂商公布的Function Calling或MCP本身不算本项目创新。产品也不承诺自动替用户作最终购车决策，仍需现实价格、试驾和配置核验。

## 4. 功能优先级与验收

P0表示形成可核验决策过程所必需；P1在过程正确后改善效率；P2依赖新来源、商业条件或更多需求证据。优先级是作者初判，依据不含虚构用户票数。

| ID/优先级 | 功能与用户价值 | 依据、依赖及具体验收 |
| --- | --- | --- |
| F01 / P0 | 条件账本与变更确认，减少沿用旧条件 | R02。12个参考轮次中的预算、能源、座位、L2及替换状态全部匹配；需求变更后旧预算保留为历史，筛选只使用新预算 |
| F02 / P0 | 硬筛选与来源卡片，防止合格推荐混入错误车 | R02、R03。推荐仅在当前可行集合内；型号/配置/年份/价格/编号可回查；模拟属性、裸车口径和日期可见，未知值不造数 |
| F03 / P0 | 一次关键澄清与输出核验，防止格式正确而内容违规 | R01。检查JSON、推荐属于候选、来源一致和追问意图；双问题案例应被发现，正常的“A还是B”单问题不误拒；不能仅用问号计数，保留人工语义复核和有界纠正记录 |
| F04 / P1 | 参数对照与报告导出，减少复制整理 | F01–F03通过后，导出表与原始字段一致，理由和未知项可追溯；采访中观察核验用时及求助是否减少 |
| F05 / P1 | 冲突解释与软偏好排序，帮助用户理解无解和取舍 | 用户明确区分硬/软偏好；无解时不擅自放宽条件，提出一个可选调整；权重只影响合格集合内排序，不让高偏好抵消预算硬约束 |
| F06 / P1 | 处理状态、取消与失败恢复，减少重复提交 | R04。超时/限流有状态及请求编号；取消后状态明确；重试不覆盖失败记录，不悄悄扩大费用；是否需要进度提示由现场等待行为验证 |
| F07 / P2 | 联网更新、工具检索和落地价核算，扩大现实适用性 | 固定库闭环及来源授权之后；检索结果记录日期和配置，税费计算列假设；单独评测联网条件，不混入固定库基线 |
| F08 / P2 | 图片选车、多渠道推荐和商业线索 | 待真实用户需求支持；图片偏好不能代替硬约束，商业排序及合作标识需可辨识；不作为本次课程基础验收依赖 |

P0先做的原因是候选和解释一旦错误，丰富界面只会放大误导。先上联网搜索会增加数据波动与核验负担；先做图片或线索分发不能解决R01/R02。此取舍与[程群技术方案](technical-improvement.md)配合：本文描述用户可见价值，接入和纠正策略由技术负责人评审。

## 5. 方案比较与选择

| 路线 | 收益 | 成本与缺点 | 本阶段选择 |
| --- | --- | --- | --- |
| 只改提示词，所有筛选都由模型完成 | 改动少，可快速联调 | 结构和语义仍可能失配；来源核对及变更回查依赖生成结果 | 作为基线保留，不据此承诺P0已实现 |
| 固定库硬筛选＋模型解释＋后置核验 | 预算等约束可确定性判定，来源和变更有据可查 | 需要字段标准化、状态维护及语义复核，数据覆盖有限 | 作为MVP主线，先解决已知任务和证据问题 |
| 一开始接联网Agent自动检索/询价 | 可覆盖更多真实配置、价格和时效需求 | 来源冲突、链接更新、权限及费用条件更多，公平评测难 | 后续扩展，独立记录条件并验证来源质量 |

选择固定库主线是为了先验证决策过程；真实产品上线仍必须替换为经核验、持续维护的数据源。比较结果是设计判断，尚无新方案与基线的实测收益。

## 6. 验证计划与调整规则

1. **离线验收。** 用现有三场景12轮参考集核对F01/F02，另设计互相冲突、未知参数、仅一车/无车、多问题追问和价格口径歧义的补充案例。补测单列，不追溯加入原矩阵。
2. **同条件比较。** 待模型、数据、提示词与评分冻结后，对每个方案分别做两模型×三场景×三次四轮任务，即每方案18次、若比较两方案则共36次。保存版本、全部请求和失败；当前18次原始基线尚未完成，不能宣称改进已生效。代码或Schema变更须另建版本，经团队评审再使用。
3. **用户核验。** 按[采访包](guo-yuqi-interview-kit.md)执行双产品体验，记录独立/有帮助完成、发现错误、参数核验时间、求助及原话。研究界面改版收益时另比较基线与改版，交替顺序，避免把对第二次任务的熟悉误判成产品改善。
4. **发布目标。** P0参考案例检查全部通过，无编造硬参数和静默放宽条件，作为设计验收目标；质量、端到端耗时与成本同时报告。目标未达时定位规则、输入、提示词或接口问题，不能靠删失败样本提高成绩。

自动化继续使用团队四维评分口径；成功率按已发起任务作分母，token缺失不填0。学生样本只作定性线索，不能估计市场转化或全体用户满意度。如果来源回查耗时不降，优先调整来源信息组织；若用户不理解裸车/落地价，先验证预算口径确认；若需求是获得现实报价，先评估真实数据维护成本再扩展。

## 7. 交付阶段与协作

阶段一完成F01–F03的设计、离线用例与采访，依赖庄剀涵的数据字典和参考集合、关欣的核验口径。阶段二由开发成员评审实现并运行基线/方案比较，程杰与曾俊涛核对输出和统计。阶段三用有真实需求的用户及可靠车型来源检验产品机会，再决定联网和商业模式；郭昱祺将匿名反馈回填优先级，张王昊整合报告。

这是一份功能规划，未改动冻结输入、运行器或模型启用状态。当前采访、模型二实跑和改进方案实现均未完成；与本次材料状态对应的个人交付及剩余证据见[交付索引](guo-yuqi-delivery.md)。
