# 程群部分博客初稿：模型接入、统一提示词与技术改进

> 本稿只包含程群负责内容。正式发布前需由张王昊并入总博客，并在完成 18 次正式实验后替换
> 冒烟测试结论。

## 模型选择与接入记录

本组选择 DeepSeek API 平台上的两个不同模型：

| 模型 | 精确标识 | 定位 |
| --- | --- | --- |
| DeepSeek Flash | `deepseek-flash` | 通用快速模型 |
| DeepSeek V4 Pro | `deepseek-v4-pro` | 高阶能力模型 |

选择这两个模型的直接原因是它们来自同一兼容接口，便于用完全相同的请求协议和参数比较，
同时又具有不同的模型标识和能力定位。2026-11-07，我们先通过模型列表接口确认标识，再分别发出
真实聊天请求，两个服务端都回显了请求中的精确模型 ID。配置和证据分别记录在
`configs/models.json` 与 `evidence/model-smoke-2026-11-07.json`。

统一参数为 `temperature=0.0`、`top_p=1.0`、`max_tokens=4096`、关闭流式输出并启用
JSON 对象模式。初试时把最大输出设得过小，发现推理内容会先占用 token，最终答案可能为空并且
`finish_reason=length`。这说明“接口返回 200”不等于“任务成功”，评测程序必须同时检查停止原因
和输出结构。

## 统一多轮提示词

两个模型使用同一套版本化提示词：系统提示词规定只能使用固定车型库、必须保留仍有效的约束、
后续需求变更要覆盖旧约束、每个候选必须引用来源编号，并只返回 JSON；首轮用户提示加入场景和
车型库；后续轮提示加入轮次编号、用户修改和生效规则。

程序同时读取 `output_schema_v1.json`，并将 JSON Schema 嵌入系统提示词。四个提示词文件的
SHA-256 指纹为：

```text
4ffc5f7ddcac9c3aa1e03a1f33ddb9931418d93c418c573113f0c8bcf4acd811
```

每次运行记录该指纹，评审时可以核对两个模型是否真的使用同一提示词版本。后续若修改场景数据、
提示词或评分口径，团队应升级版本并记录影响，不能覆盖旧记录后继续沿用相同结论。

## 上下文和错误处理

模型接入层不自己保存会话。一次任务内，运行框架必须持续传入完整消息列表；不同独立运行创建
新的消息列表。这样既保留多轮上下文，又避免上一次运行通过对象或缓存污染下一次实验。

接入层统一处理鉴权、超时、限流和服务端错误。普通的错误请求不会重试；`408`、`409`、`429`
和 `5xx` 使用有限次指数退避。每次请求记录服务端模型 ID、响应 ID、token 用量、耗时、
`finish_reason` 和重试次数。密钥只从环境变量读取，配置文件和公开记录不保存真实密钥。

## 一项技术改进：结构化输出校验与受控修复

购车任务的后续评分需要稳定读取候选车型、约束和证据编号，但大模型常见问题是添加 Markdown
围栏、遗漏字段、最终推荐和下一问题同时出现，或者输出被长度上限截断。仅靠提示词“请输出 JSON”
无法证明结果真的可用。

本组实现的是“JSON 模式 + Schema 校验 + 最多一次纠正”：模型返回后，程序先解析 JSON，再检查
字段、类型、来源编号和停止原因；失败时追加一条统一纠错消息，让同一模型重新回答一次。若仍失败，
则保留原始响应并标记失败，不人工补造结果。纠正消耗的 token、延迟和次数都会计入总成本，避免给
某个模型额外的隐式优势。

我们比较了三个备选方案：

| 方案 | 特点 | 处理 |
| --- | --- | --- |
| 仅提示词要求 JSON | 最简单，格式约束最弱 | 作为 A/B 消融基线 |
| JSON 模式 + 校验 + 一次纠正 | 结构保障和工程复杂度较平衡 | 当前采用 |
| 工具调用或平台严格 Schema | 约束可能更强，但跨平台能力不一，且改变任务机制 | 后续扩展 |

验证不能只看一次成功。建议另做 36 次补充消融，两个条件分别是仅提示词约束和当前改进；
比较 JSON 解析率、Schema 通过率、首次通过率、纠正成功率、token 与延迟开销，并复核业务约束
符合度。实现门槛、样本量和计算方式需在正式运行前冻结。

## 初步结果与适用条件

2026-11-07 的双模型冒烟测试各运行一次。`deepseek-flash` 使用 3521 token、耗时 12.500 秒，
`deepseek-v4-pro` 使用 4468 token、耗时 31.938 秒；两者都正常停止并通过 Schema，本次均未
触发纠正。两个模型都排除了超预算车辆，并引用了模拟车型库中的真实来源编号。前者推荐纯电轿车，
后者更重视补能灵活性，推荐插电混动 SUV。

这组结果只能说明两个模型已经能够被同一框架稳定调用，不能据此宣布稳定性或准确性排名。
正式结论应基于至少 18 次完整多轮任务，并同时报告成功率、波动、延迟、token 和评分结果。
从冒烟现象看，高能力模型当前耗时和输出 token 更多；是否值得这些额外成本，需要结合正式任务中
约束符合度、多轮一致性和失败案例来判断。
